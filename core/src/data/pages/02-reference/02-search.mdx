## General search process

Every search request is written in **search steps** - smaller execution units, which are specialized for one specific
database or technology. Results of earlier search steps are available to later search steps as input parameters,
allowing **cross-database search logic**.

**Note**: Due to security reasons, most search steps are limited in scope. Specific details and workarounds can be found
on their detail pages.

## Search steps

### Elasticsearch Query DSL Mixin

Executes search queries against **Elasticsearch**. Great for full text search, explorative search requests, small logic
etc.

### Cypher Path

Executes search queries against **Neo4j**. Great for structural search, e.g. "list all comments on blog post X".

### Element Hydration

Converts a list of element ids to a collection response, containing elements and all their properties.  
This step is mostly used to convert results of other search steps to collection responses usable by clients.

## Examples

### Simple full text search

import simpleFullTextSearch from '../assets/simple-full-text-search.json';
import simpleFullTextSearchHeader from '../assets/simple-full-text-search.txt?raw';

In this example, only Elasticsearch is queried for all elements, whose `description`-property contains the word
`lily`.  
The `element-hydration`-step only makes sure, that the results from Elasticsearch are correctly hydrated and returned.

See also [Elasticsearch's documentation about the match query clause](https://www.elastic.co/docs/reference/query-languages/query-dsl/query-dsl-match-query).


```json
{
  "debug": true,
  "steps": [
    {
      "type": "elasticsearch-query-dsl-mixin",
      "query": {
        "match": {
          "description": {
            "query": "lily"
          }
        }
      }
    },
    {
      "type": "element-hydration"
    }
  ]
}
```

### Simple path search

In this example, only Neo4j is queried for all paths, which satisfy `(:Plant)-[:HAS_TAG]->(:Tag {name: "blue"})` - i.e.
all plants, which are tagged `blue`.  
The `element-hydration`-step only makes sure, that the results from Neo4j are correctly hydrated and returned.

import simplePathSearch from '../assets/simple-path-search.json';
import simplePathSearchHeader from '../assets/simple-path-search.txt?raw';

```json
{
  "debug": true,
  "steps": [
    {
      "type": "cypher-path-subset",
      "query": "MATCH path=((:Plant)-[:HAS_TAG]->(:Tag {name: \"blue\"})) RETURN path"
    },
    {
      "type": "element-hydration"
    }
  ]
}
```

<SearchResponseCard
    responseBody={simplePathSearch}
    responseHeaders={simplePathSearchHeader}
    graphLayout="force"
></SearchResponseCard>

The graph view can actually display a graph, because we queried relations and all paths share a common node - the tag
`blue`.

### Combined full text and path search

An example how results from Elasticsearch - all elements whose description contain the word `lily` - are feed as input
parameters to Neo4j, which then expands the results to the path `(:Plant)-[:IS_MEMBER_OF*..]->(:Taxon)`.  
Note that because we map Elasticsearch's results to only `:Plant`-nodes, we filter out other results from Elasticsearch,
e.g. Taxons which also contain the word `lily`.

import combinedFullTextAndPathSearch from '../assets/combined-full-text-and-path-search.json';
import combinedFullTextAndPathSearchHeader from '../assets/combined-full-text-and-path-search.txt?raw';

```json
{
  "debug": true,
  "steps": [
    {
      "type": "elasticsearch-query-dsl-mixin",
      "query": {
        "match": {
          "description": {
            "query": "lily"
          }
        }
      }
    },
    {
      "type": "cypher-path-subset",
      "query": "UNWIND $stepResults[0].elements AS element MATCH path=((plant:Plant)-[:IS_MEMBER_OF*..]->(:Taxon)) WHERE plant.id = element.id RETURN path"
    },
    {
      "type": "element-hydration"
    }
  ]
}
```

<SearchResponseCard
    responseBody={combinedFullTextAndPathSearch}
    responseHeaders={combinedFullTextAndPathSearchHeader}
></SearchResponseCard>

Due to the unlimited path length, the resulting graph can become quite big.

Duplicated nodes etc. are already filtered out by the API itself, as can be seen in the debug view.
